## Phase 1: ingest

**Built**
- `aml.data.ingest`: reads each CSV line verbatim into DuckDB with its 0-based `row_index`, then parses it into `transactions` with snake_case columns. The two `Account` columns are mapped by position to `from_account` / `to_account`. Bank codes stay as text (they have leading zeros).
- `aml.data.txn_id`: `txn_id = sha256(raw_line | row_index)[:16]`. The source has no ID column, and 9 groups of exact-duplicate rows (18 rows) need the row index to break ties. Ingest asserts uniqueness; a Python reference implementation is tested against the SQL.
- `aml.data.fx`: static `USD_PER_UNIT` table derived from the dataset's own cross-currency rows (median implied rate vs USD). Originals are kept as `DECIMAL(38,6)`; `amount_*_usd` is `DECIMAL(38,2)`.
- `aml.data.customers`: seeded Faker profiles (name, address, DOB, occupation), one per **(bank, account)**, because 8 account IDs appear under two banks.
- `aml.data.split`: `split = 'train'` if `timestamp < 2022-09-08`, else `'test'`.
- `aml.eval.labels` / `aml.eval.patterns`: the labels live in a separate DuckDB schema, `eval.txn_labels(txn_id, is_laundering)` and `eval.laundering_attempts(attempt_id, typology, txn_id)`. Pattern rows are matched to transactions by exact line text, with the n-th duplicate paired to the n-th occurrence.
- `tests/test_label_leakage.py`: scans `src/aml` (except `eval/`) for label identifiers, the `eval.` schema, and `aml.eval` imports, with no exemptions. `aml.data` parses only the first 10 fields and never names the target column.
- `scripts/ingest.py` rebuilds everything (~90 s, ~3 GB peak RSS) and regenerates the report block below.

**Split choice.** Daily volume is uneven: Sep 1 alone holds 22% of rows, Sep 3–4 and Sep 10 are light, and Sep 11–18 has only 1,108 rows. A midnight cut keeps whole days of traffic together. Midnight Sep 8 gives 73.5% / 26.5%, the closest day boundary to 70/30 (Sep 7 would give 64/36). Sep 1–7 also has full weekday and weekend cycles for fitting thresholds.

**Open issues**
- The test set's laundering rate (0.160%) is about twice train's (0.081%). Much of that comes from the Sep 11–18 tail: 1,108 rows, of which 655 (59%) are laundering. These are attempts finishing after normal traffic stops. Precision on test will look better than it would in production; evaluation should also report metrics for Sep 8–10 only.
- Only 62% of laundering rows (3,209 / 5,177) belong to a typed attempt in the patterns file. Per-typology recall is therefore measured on that subset; the remaining 1,968 positives are untyped.
- 4,727 transactions have `amount_paid_usd = 0.00`, because sub-cent amounts round to zero at 2 dp. The original amounts are exact. This only matters if a rule divides by USD amounts.
- Customer profiles are deterministic for the Faker version pinned in `uv.lock`; upgrading Faker will change the generated names.
