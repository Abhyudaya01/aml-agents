## Phase 1: ingest

**Built**
- `aml.data.ingest`: reads each CSV line verbatim into DuckDB with its 0-based `row_index`, then parses it into `transactions` with snake_case columns. The two `Account` columns are mapped by position to `from_account` / `to_account`. Bank codes stay as text (they have leading zeros).
- `aml.data.txn_id`: `txn_id = sha256(raw_line | row_index)[:16]`. The source has no ID column, and 9 groups of exact-duplicate rows (18 rows) need the row index to break ties. Ingest asserts uniqueness; a Python reference implementation is tested against the SQL.
- `aml.data.fx`: static `USD_PER_UNIT` table derived from the dataset's own cross-currency rows (median implied rate vs USD). Originals are kept as `DECIMAL(38,6)`; `amount_*_usd` is `DECIMAL(38,2)`.
- `aml.data.customers`: seeded Faker profiles (name, address, DOB, occupation), one per **(bank, account)**, because 8 account IDs appear under two banks.
- `aml.data.split`: `split = 'train'` if `timestamp < 2022-09-08`, else `'test'`.
- `aml.eval.labels` / `aml.eval.patterns`: the labels live in a separate DuckDB schema, `eval.txn_labels(txn_id, is_laundering)` and `eval.laundering_attempts(attempt_id, typology, txn_id)`. Pattern rows are matched to transactions by exact line text, with the n-th duplicate paired to the n-th occurrence.
- `tests/test_label_leakage.py`: scans `src/aml` (except `eval/`) for label identifiers, the `eval.` schema, and `aml.eval` imports, with no exemptions. `aml.data` parses only the first 10 fields and never names the target column.
- `scripts/ingest.py` rebuilds everything (~90 s, ~3 GB peak RSS) and regenerates the report block below.

**Split choice.** Daily volume is uneven: Sep 1 alone holds 22% of rows, Sep 3–4 and Sep 10 are light, and Sep 11–18 has only 1,108 rows. A midnight cut keeps whole days of traffic together. Midnight Sep 8 gives 73.5% / 26.5%, the closest day boundary to 70/30 (Sep 7 would give 64/36). Sep 1–7 also has full weekday and weekend cycles for fitting thresholds.

**Open issues**
- The test set's laundering rate (0.160%) is about twice train's (0.081%). Much of that comes from the Sep 11–18 tail: 1,108 rows, of which 655 (59%) are laundering. These are attempts finishing after normal traffic stops. Precision on test will look better than it would in production; evaluation should also report metrics for Sep 8–10 only.
- Only 62% of laundering rows (3,209 / 5,177) belong to a typed attempt in the patterns file. Per-typology recall is therefore measured on that subset; the remaining 1,968 positives are untyped.
- 4,727 transactions have `amount_paid_usd = 0.00`, because sub-cent amounts round to zero at 2 dp. The original amounts are exact. This only matters if a rule divides by USD amounts.
- Customer profiles are deterministic for the Faker version pinned in `uv.lock`; upgrading Faker will change the generated names.

## Phase 2: alert generation

**Built**
- `aml.alerts.windows`: each transaction becomes an `in` leg and an `out` leg (self-transfers dropped). Windows are 7-day tumbling blocks anchored on the split date: W0 = Sep 1–7 (train), W1 = Sep 8–14 and W2 = Sep 15+ (test). `build_legs` raises if any window mixes splits.
- `aml.alerts.features`: per (bank, account, window), computed from that window's legs only:
  - counts, in/out USD
  - fan-in/out degree
  - cross-currency share
  - 7 payment-format shares
  - `max_24h` and `burst_ratio` (velocity)
  - amounts in [$9k, $10k) (structuring)
  - round-amount share
  - `n_pass_through`: in-legs followed within 48h by an out-leg within ±10% to a different counterparty

  773,711 account-windows in about 3s.
- `aml.alerts.rules`: FAN_IN, FAN_OUT, STRUCTURING, VELOCITY_SPIKE, PASS_THROUGH. Each rule is a single SQL condition plus an evidence query, and the evidence goes to `rule_hits(rule_id, txn_ids)`. Scoring, tuning and evidence all use the same condition.
- `aml.alerts.anomaly`: IsolationForest (200 trees, seed 0) on log1p features, **fit on W0 only**. The percentile is taken against the W0 score distribution.
- `aml.alerts.records`: the `Alert` pydantic model and `alerts` table. `combined = 0.6 × min(1, Σ fired rule weights) + 0.4 × anomaly percentile`, with hand-set weights. `alert_id` is a hash of (bank, account, window_start).
- `aml.eval.tuning`: coordinate ascent over train-feature quantiles (p90–p99.9 or disabled) for each rule threshold. It maximizes train recall at ≤ 10 alerts per 1k train windows; the cutoff is re-derived from the budget for each candidate. The output is `artifacts/thresholds.json`, committed and hashed; detection code reads only that file.
- `aml.eval.alert_metrics`: precision, recall, alerts per 1k accounts and per 1k windows, and txn-level recall (cited in `rule_txn_ids`, or touching an alerted window). Per-typology recall at unit and attempt level, rule breakdown, and rules-only / anomaly-only ablations, each with its own train-budget cutoff.
- Leakage tests:
  - flipping every test label leaves the tuned thresholds unchanged
  - adding a test-period outlier leaves the anomaly model's train scores unchanged
  - a window that mixes splits is rejected
  - the existing scanner keeps `aml.alerts` from importing `aml.eval`

**Reading the baseline**
- **Lift, not accuracy.** About 1% of train windows are positive (4,064 / 412k), and the budget (4,121 alerts) is about the same size. A perfect detector would therefore reach ~100% recall, so 5–7% recall is weak. 10.4% test precision is still about 10× the base rate.
- **The tuner turned off three rules** (FAN_OUT, STRUCTURING, VELOCITY_SPIKE). At a 1% budget each would spend alert slots at lower train precision than FAN_IN ≥ 7. FAN_OUT suffers most from hub accounts (out-degree up to 14k).
- **PASS_THROUGH is the sharpest rule** (93% test precision) but fires only 15 times at ≥ 14 pass-throughs. Its threshold sits at the top of the train distribution, so a second rule tier with a lower threshold is the obvious next experiment.
- **The anomaly score adds almost nothing.** The cutoff (0.3999) means anomaly-only alerts need the 99.97th percentile, and anomaly-only scores 3% precision. The IsolationForest flags unusual *volume*, not unusual *structure*.
- **The test week uses less of the budget** (3.8 vs 10 per 1k windows). Fewer accounts reach fan-in ≥ 7 in W1, a distribution shift that a train-only calibration can't anticipate.
- **Typologies:** FAN-IN (58% of attempts) and SCATTER-GATHER (48%) are caught; RANDOM, BIPARTITE, CYCLE and FAN-OUT are mostly missed. No rule looks beyond one account's own legs, and these patterns are multi-hop. Graph features (Phase 3+) should target them.
- **The W2 tail doesn't distort these numbers.** test and test_w1 match closely because the combined detector raises no alerts on W2's 88 windows.

**Open issues**
- Coordinate ascent is greedy and started at p99; a broader search on train could do better. The thresholds file pins the current result.
- Velocity needs both of its thresholds, so turning one off disables the rule. The tuner explores this, but the two are coupled.
- Rule evidence for hub accounts can list thousands of txn_ids per alert; Phase 3 tools will need to summarize it.
- `round_share` has almost no signal in this simulator (360 round amounts ≥ $1k in 5M rows).
